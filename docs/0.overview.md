## 1. Product in one paragraph

Most anti-scam tools only *warn* people. **Scam Dojo trains, checks and recovers.** It is a three-mode web app (mobile-first, installable PWA) for everyday users in India/JAPAC:

| Mode | User question | What happens |
|---|---|---|
| **Train** | "Could I be fooled?" | A *Scammer agent* runs a realistic, adaptive scam simulation (UPI collect request, fake KYC, fake job offer, digital-arrest call). A hidden *Observer agent* reads each of the user's replies and steers the pressure. A *Coach agent* then produces a replay-style debrief and a **Resilience Score** that moves the user up a belt ladder (white → black). |
| **Check** | "Am I being scammed right now?" | User pastes a message or uploads a screenshot / short video / voice note. A pipeline of an *Indicator agent* (regex + local knowledge base + optional Google Web Risk) and a *Scam Analyst agent* (Gemini multimodal) returns a risk verdict, highlighted red flags, and what to do in the next 5 minutes. |
| **Recover** | "I already got scammed." | A calm guided intake → *Recovery Planner agent* creates a time-boxed action plan (golden-hour steps first), with India-specific, verified contacts and copy-ready complaint drafts; a *Recovery Chat agent* answers follow-ups. |

Cross-mode loops (the innovation story): **Check → "Train me on this"** (a *Scenario Forge agent* turns a real scam you just checked into a custom drill) and **Recover → recommended drills** (weakest tactics from your history).

One-liner for the pitch: **"Most tools only warn people. Scam Dojo trains them, checks for them, and helps them recover."**

## 3. Key technology decisions (and why)

| Area | Decision | Rationale |
|---|---|---|
| LLM | **Gemini on Vertex AI** (prod) / Gemini API key (local). Model IDs are **env-configurable**: `MODEL_FAST`, `MODEL_LITE`, `MODEL_PRO`. | The source plan says "Gemini 2.0 / 1.5 Pro". Those generations are likely deprecated by now. **Check Vertex AI docs at build time** and set the newest GA Flash / Flash-Lite / Pro. Defaults in `.env.example`: `gemini-2.5-flash`, `gemini-2.5-flash-lite`, `gemini-2.5-pro`. |
| Agent framework | **Google ADK (Python)** | Core of the 40% score. |
| API | **FastAPI** on **Cloud Run** (region `asia-south1`) | Managed, scales to zero, streams SSE. |
| Frontend | **Next.js (App Router) + TypeScript + Tailwind v4 + shadcn/ui + Motion**, static export on **Firebase Hosting** | Fast global CDN, simple, robust for demo day. |
| Auth | **Firebase Authentication**: Google Sign-In **+ Anonymous guest** (judges can start in one tap) | Zero friction demo. |
| User data | **Firestore** (profiles, sessions, checks, recovery plans, progress, global counters) | Real-time, per-user, serverless; source of truth. |
| Reference/knowledge data | **SQLite (`knowledge.sqlite`) bundled read-only in the API image**, with FTS5 | Scam playbooks, scenarios, helplines, regex rules are static, relational, searchable, and must work offline/in tests. Google DB is *not needed* here. |
| Cache / burst limits | **SQLite in `/tmp` (ephemeral)** | Response cache for demo-mode + per-instance rate limiting. Explicitly *not* durable. |
| Local dev | `STORE=sqlite` repository + dev auth → full app runs with **no GCP project** (only a Gemini API key) | Lets the build agent iterate fast and tests run in CI. |
| Backend statelessness | Every agent call uses a **fresh in-memory ADK session seeded from Firestore state** | Cloud Run can scale horizontally without sticky sessions. |
| Security | Firebase ID token on every API call; Firestore rules deny client writes; PII scrubbing before LLM + storage | Safe for a public demo. |
| Observability | Structured JSON logs (Cloud Logging) + in-app **trace events** | Debuggable on stage. |

## 6. Phased build plan with acceptance criteria

Mapped to the 4-day sprint. Backend and frontend can proceed in parallel once `6.api-contract.md` is fixed; generate TS types from the FastAPI OpenAPI.

### Phase 0 — Bootstrap (Day 1, morning)
- Create monorepo, tooling (`pnpm`, `uv` or `pip-tools`, `ruff`, `mypy`, `pytest`, `eslint`, `prettier`), `Makefile`.
- Build `knowledge.sqlite` from `data/seed/*.yaml` (`make kb`) — schema in `5.database.md`.
- Backend skeleton with `/healthz`, config, structured logging, dev auth, `SqliteRepo`.
- Frontend skeleton with tokens, fonts, layout shell, i18n provider, theme toggle.
- **Accept:** `make dev` starts both apps; `/healthz` OK; home page renders with real design tokens in light + dark; `make test` passes (even if trivial).

### Phase 1 — Train backend (Day 1)
- Scenario loader, Observer + Scammer `SequentialAgent` turn pipeline with SSE streaming, Coach agent, deterministic scoring, belts, `/v1/train/*` endpoints.
- PII scrubber + safety break.
- **Accept:** a `curl`/pytest scripted conversation reaches `user_won` and `user_fell` for each scenario; debrief JSON validates against schema; scoring unit tests pass; Hindi replies work.

### Phase 2 — Train frontend (Day 1 → Day 2 morning)
- Home hub, scenario picker, chat stage with channel skins, streaming, pressure meter, hang-up, debrief replay, belt reveal.
- **Accept:** a full Train run in the browser on a 360px viewport; streaming tokens visible; debrief annotated; keyboard + screen-reader usable.

### Phase 3 — Check mode (Day 2)
- Indicator agent, Analyst agent (multimodal), `/v1/check` SSE, upload UI with image/video/audio, verdict screen, golden-set eval (≥ 90% correct class on the 30-case set).
- **Accept:** screenshot of a fake KYC SMS → `likely_scam` with quoted red flags; a genuine bank OTP SMS → `likely_safe`; prompt-injection test passes.

### Phase 4 — Recover mode (Day 2)
- Intake wizard, resource selector, Recovery Planner (structured), step checklist persistence, copy-ready drafts, Recovery Chat.
- **Accept:** plan always leads with time-critical steps; every phone number/URL in the plan exists in `resources` (automated test); plan survives refresh (Firestore).

### Phase 5 — Persistence, Auth, Dashboard, i18n (Day 3, morning)
- Firebase Auth (Google + anonymous + account linking), `FirestoreRepo`, rules, dashboard endpoint and UI, streaks, EN/HI complete.
- **Accept:** guest → Google upgrade keeps history; dashboard shows real trend after 3 sessions; switching language mid-session changes UI and agent output.

### Phase 6 — Polish & demo features (Day 3, afternoon)
- Trace panel, demo mode (`/demo`, cached fallback), share card, Scenario Forge, PWA, loading/empty/error states, motion pass, accessibility pass.
- **Accept:** Lighthouse mobile: Performance ≥ 85, Accessibility ≥ 95, Best Practices ≥ 95; no console errors.

### Phase 7 — Deploy, QA, pitch (Day 4)
- Cloud Run + Firebase Hosting deploy, budget alert, min-instance = 1 during the event, e2e tests, backup video, pitch deck, README with architecture diagram.
- **Accept:** `8.demo-and-qa.md` checklist fully ticked.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Model latency on stage | Flash-Lite for Observer; Flash for Scammer; Pro only for Coach/Recovery (non-interactive). `--min-instances=1 --cpu-boost`. Demo-mode cache. Backup video. |
| Quota / 429 | Retry with jitter (tenacity), per-user daily caps, fallback to a smaller model, friendly error with retry button. |
| Hallucinated helplines | Resources are **only** from SQLite (`resources` table); planner prompt forbids others; automated test asserts it. |
| Harmful output from Scammer | Fictional entities only, no real numbers/URLs, safety-break rule, output filter, eval red-team set. |
| Users typing real data | Client + server PII scrubbing; banner "Use made-up details here". |
| Hindi quality | Native-quality review of top 40 UI strings + prompt instruction on register (see design §9). |
| Network failure at judging | `DEMO_MODE=cached` + offline-capable pre-recorded video. |
| Over-scoping | Strictly follow MUST/SHOULD/STRETCH. Cut STRETCH first. |
