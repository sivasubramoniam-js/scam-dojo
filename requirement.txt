SCAM DOJO
Google AI Ecosystem Catalogue + Comprehensive Anti-Scam Web Application Blueprint
Research and planning edition • 17 October 2026 • For a two-person AI Builder Cup team
Executive decision
Build a defensible, evidence-led scam triage assistant, not a tool that claims to certify safety. The MVP should accept suspicious messages, URLs and screenshots; extract indicators; check known unsafe URLs using an appropriately licensed reputation service; produce a calibrated risk assessment with evidence; and offer concrete protective next steps. A convincing working flow matters more than integrating every available Google service.
Competition requirements and timing
The official AI Builder Cup themes page lists BFSI fraud/risk as an eligible theme; prototypes must meaningfully use Google AI and be deployed via Google Cloud/Cloud Run or Firebase. Required materials include a proposal PDF and a three-minute demo link. The published submission deadline is 18 October 2026. Confirm submission portal status directly before relying on the deadline. Part II — SCAM DOJO product design
Positioning and user promise
SCAM DOJO helps people pause, inspect, and verify suspicious digital interactions. It explains observable red flags, distinguishes verified findings from uncertainty, and gives safe next steps. It must never guarantee that a link, payment, caller, or person is safe. Focus initial coverage on phishing links, impersonation messages, fake job offers, delivery/payment scams, QR-payment pressure, investment promises, and customer-support impersonation.
1. Scam message analyzer
User flow / implementation: Paste SMS, WhatsApp or email text. Gemini extracts requested action, urgency cues, impersonation claims, links, phone numbers and payment requests; return evidence snippets and a reasoned assessment.
Google stack: Gemini structured output, Cloud Run, Firestore   |   Phase: MVP
2. Screenshot intelligence
User flow / implementation: Upload screenshot; multimodal Gemini or Vision OCR extracts text and interface cues. Mask contact details by default. Display extracted text for correction before analysis.
Google stack: Gemini vision, Cloud Vision, Cloud Storage   |   Phase: MVP
3. URL reputation checks
User flow / implementation: Parse and normalize a URL; check domain and redirects using a safe backend workflow, then query Safe Browsing or Web Risk subject to licensing. Do not visit malicious sites in a user browser or execute active content.
Google stack: Google Safe Browsing / Web Risk, Cloud Run, Cloud Tasks   |   Phase: MVP
4. Explainable risk meter
User flow / implementation: Combine reputation match, message cues, impersonation signals, and uncertainty in an explicitly labeled heuristic score. Show observed evidence, not false probability of fraud.
Google stack: Gemini, deterministic rules, structured JSON   |   Phase: MVP
5. Protective action guide
User flow / implementation: Tailor actions: do not click, verify via independently sourced official contact, do not share OTP/PIN, contact bank, block/report; urgent account compromise flow.
Google stack: Gemini, curated safety playbooks   |   Phase: MVP
6. Source-backed verification
User flow / implementation: Ground claims about companies or current scam advisories in official public sources; show dates, citations and whether verification failed.
Google stack: Gemini Search grounding, URL Context   |   Phase: High
7. Fake job offer checker

Google stack: Gemini, Search grounding   |   Phase: High
8. Payment/UPI scam coach

9. Multilingual detection

Google stack: Gemini, Cloud Translation   |   Phase: High
10. Voice note analyzer

Part III — Architecture and operational detail
Frontend (React + Material Design) → Firebase App Check / Authentication (optional guest mode) → Cloud Run API → input validation and redaction → modality extraction (Gemini/Vision/Speech) → URL reputation lookup (licensed Safe Browsing or Web Risk) → deterministic rules + Gemini reasoning → structured assessment → user action cards. Store only consented redacted results in Firestore; short-lived uploads in Cloud Storage. Secret Manager holds credentials; Cloud Logging records technical telemetry without raw scam messages.
Recommended assessment schema
Input type; extracted indicators; risk category (low / caution / high / unknown); observed evidence with exact snippets; verified external matches with timestamp and source; uncertainty and limitations; recommended safe actions; privacy/redaction status. Never expose an unsupported numeric confidence as a statistical fraud probability.
Scoring and quality methodology
Keep known reputation matches separate from heuristic language cues.
Use a test set including genuine bank alerts, legitimate job offers and genuine delivery messages to measure false positives.
Measure precision, recall, false-positive rate, citation correctness, redaction success and response latency.
Label ambiguous inputs as inconclusive and ask for more context rather than fabricate evidence.
Defend against prompt injection embedded inside suspicious messages or pages: treat user-submitted material as untrusted data.
Do not fetch arbitrary URLs without SSRF defenses, domain/IP restrictions, redirect limits and isolated infrastructure.
Do not expose user uploads, passwords, OTPs, payment credentials or unredacted personal data in logs or demo materials.
India-focused response design
Offer independently verified links to the official National Cyber Crime Reporting Portal and the 1930 financial cyber-fraud helpline where applicable; remind users to contact their bank immediately after suspected payment fraud. Provide general safety education rather than legal or financial guarantees. The product should not request Aadhaar numbers, OTPs, UPI PINs, bank passwords or full card data.
Part IV — Practical 24-hour hackathon implementation
0–2 hours — Freeze scope: text + screenshot + URL check + explainable result + action guidance. Prepare 12 synthetic cases and 5 benign controls.
2–5 hours — Developer creates React UI and Cloud Run backend; domain expert writes risk rubric, safe advice and expected results.
5–9 hours — Integrate Gemini structured output and screenshot extraction; build deterministic URL parsing and reputation integration if approved and available.
9–13 hours — Implement evidence display, redaction, safe fallback behavior and feedback form. Add authentication only if necessary.
13–17 hours — Deploy to Cloud Run/Firebase; configure Secret Manager, App Check, limits, CORS and basic logging.
17–20 hours — Test adversarial examples, false positives, mobile UX, broken links and empty uploads; fix critical bugs.
20–24 hours — Record a three-minute demo; create proposal PDF; verify public link and submission requirements.
Roles: domain lead vs developer
Domain lead: define scam taxonomy, collect synthetic scenarios, draft explainable safety language, verify official reporting guidance, evaluate outputs, design pitch and record demo. Developer: frontend, Gemini integration, Cloud Run, URL safety, database, security, tests and deployment. Both: agree on MVP, validate end-to-end flow, rehearse demo.
Suggested three-minute demo
0:00–0:25: real-world problem and why existing warning tools miss conversational pressure. 0:25–1:10: analyze a suspicious job-offer screenshot. 1:10–1:55: analyze a URL and show independent reputation status plus uncertainty. 1:55–2:25: show safe action guidance and multilingual explanation. 2:25–3:00: technical architecture, safeguards, measured test results and impact.
Part V — Prioritization and tradeoffs
Must-have: Gemini multimodal understanding, structured output, deterministic URL parsing, secure backend, Firebase/Cloud Run deployment, safe next steps, evidence and uncertainty. Strong next additions: search grounding, QR decoding, Hindi, scam education, document extraction. Post-competition: voice, multi-agent coordination, community reporting, browser extension, advanced analytics and optional live monitoring. Imagen, Veo and Lyria are not core to scam detection; use them only for educational content if justified.
Licensing, availability and caveats
Safe Browsing and Web Risk have different permitted uses, eligibility and commercial licensing. Confirm the correct service before deployment. Search grounding and URL Context are retrieval aids, not reputation verdicts. Maps, YouTube, Workspace, retail and ML tools from Part I are optional; most should not be included in the first version. Google products and quotas can change, and a product catalogue does not imply every feature is universally available.
